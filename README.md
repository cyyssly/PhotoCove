# PhotoCove — 本地摄影作品展示站

桌面应用（Electron）：作品集瀑布流 / 时间轴 / 相册集 / 地图点位 / Lightbox 大图浏览，EXIF 信息展示，暗色与亮色主题。
照片始终留在原目录，只读不写；索引和缩略图存在程序目录的 `data\` 里，整个文件夹拷走就跟着走。

> v18 起**只保留桌面版**。原来的浏览器版本（File System Access API）已经移除：
> 它拿不到绝对路径、解不开 HEIC、授权每次启动都会失效，而这些限制由浏览器沙箱决定、修不好。
> 现在直接双击 `index.html` 会看到一句「请从桌面窗口启动」。
>
> v19 把补 GPS 收回应用内：地图选点 / 地名搜索 / 批量写入 EXIF 一体完成，
> 不再需要任何外部工具。
>
> v20 新增「帮助」页：说明文档与原来藏在设置页折叠块里的「使用须知」合并，
> 左边常驻目录、右边卡片正文，设置页只留一行指向帮助的链接。
>
> v21 设置页「图片库」新增「相册识别」粒度：可在「下一级 / 下两级 / 下三级」之间切换
> 相册集与「全部相册」筛选按目录的哪一层切分。默认「下一级」即第一层子文件夹，
> 它下面更深的子文件夹都并进同一相册；粒度保存后立即重算，无需重新扫描。
> 相册集右上角的统计改为「N 个相册/M 张照片」，相册数与下方卡片一致；其他视图仍只显示照片数。
> 地图「无位置信息」改按相册聚合；相册列表按相册名顺序排列，进入相册后的待处理照片按文件名顺序排列，
> 均不提供自定义排序。补位置右栏工具行的返回 / 列表 / 缩略图三个按钮全部图标化，
> 缩略图模式每行两张、正方形裁切，横竖图都填满不变形，选择会记住。
> 作品集右上角新增排序按钮：图标跟随当前方式，可切 顺序 / 逆序 / 最新 / 最旧 / 最大 / 最小 /
> 随机 / 新图优先 8 种（方式与算法对齐 FrameFlow），选择存进设置、重启沿用，只影响作品集排列；
> 最新 / 最旧按拍摄日期（EXIF）为准，不再参考文件修改时间，没有拍摄日期的照片排在最后。
> 相册集右上角也加了排序按钮，只支持 顺序 / 逆序 / 随机 3 种，选择单独存设置。
>
> v22 地图「地名搜索」改为中文具体地名优先走百度地图 POI：OSM 缺少「广州国际会议展览中心」
> 这类常用别名，百度按常用名能搜准；坐标换算回 WGS-84 后再与 EXIF、底图对齐。
> 百度不可用时自动退回 OpenStreetMap，并在候选上方提示来源，不再静默降级。

## 启动

**已打包的绿色版**：双击 `dist\win-unpacked\PhotoCove.exe`。不需要 Node，也不需要 `npm install`；整个 `win-unpacked` 文件夹可以直接拷到别的电脑上用，`data\` 随文件夹一起搬走。

**从源码运行**（开发用）：

```bat
npm install          :: 只需一次
启动 PhotoCove.bat    :: 之后双击这个
```

也可以在项目目录执行 `npm start`。

## 日常使用

- 打开就是上次扫描的结果，**不做任何自动扫描**。要更新时到「设置 → 图片库」点对应目录的「重新扫描」
- **扫描只读文件信息与分辨率**（解析文件头，不解码像素），为几万张照片建索引也只要几秒到几十秒；扫描期间右下角浮卡显示进度，随时可点「取消」，已扫部分正常入库
- **缩略图按需生成**：浏览到哪张才解码哪张（滚动进入视口时生成，打开大图时生成高清预览），生成后缓存，第二次访问立即显示
- **分批加载**：每个视图每次只渲染 36 张，滚到底自动追加。几万张照片也能秒开
- 点图片进入大图：`←` `→` 或滚轮切换，`Esc` 关闭，左键点击图片进入全屏；底部缩略图条可直接点选
- 拍摄时间取自 EXIF，无效时间自动过滤（有些工具会写出 1899 年之类的畸形时间戳，宁缺勿错）
- RAW 也读文件头的 EXIF（机型 / 时间 / 光圈 / ISO / GPS），只是不解析宽高；旧索引里的 RAW 没有这些字段，点一次「重新扫描」会自动补齐，之后仍走增量快路径
- 顶栏右侧在滚动超过 3 屏后出现「↑ 返回顶端」

### 地图与补 GPS

底图用**免 API Key 的 OSM 瓦片**，随项目本地存放（`assets/vendor/leaflet/`），多源自动降级：`tile.openstreetmap.de` → `tile.openstreetmap.org` → `OpenTopoMap`。三者都是 Web 墨卡托 / WGS84，与照片经纬度一致、无偏移。瓦片请求只发送瓦片坐标，不上传照片、文件名或经纬度。

**补 GPS 在应用内完成**，不再需要外部工具：

- 地图页左上角可直接搜地名（回车或点「搜索」，<kbd>↑</kbd><kbd>↓</kbd> 选、回车定位），搜索框右边是放大 / 缩小按钮；在图上点一下落下可拖拽的标记，右下角坐标条显示当前选点
- 地图页右上角「N 张照片无位置信息」（点击后这一行原地向下展开，面板右上角 <kbd>▴</kbd> 收起），按相册聚合（细分粒度与设置页的「相册识别」一致），点一行就在大地图右侧打开待处理列表（补位置工作台），只载入该相册里**缺 GPS** 的照片，已有坐标的不会被覆盖；工具行最右端是三个图标按钮：**返回**箭头退回相册列表接着挑下一个，靠右的**列表** / **缩略图**切换右栏显示样式（缩略图每行两张、正方形裁切，横竖图不变形）；地图会先落到同相册已有 GPS 照片的大致位置
- 在图上点一下取坐标（标记可拖动微调），或搜地名——走 OpenStreetMap 的 Nominatim，返回 WGS-84，与照片坐标和底图同一坐标系，**不需要 GCJ-02/BD-09 那套纠偏**
- 右栏可全选/单选，一次写入整个相册；大图页按 <kbd>G</kbd> 把单张送进工作台，按 <kbd>R</kbd> 在资源管理器中显示
- 写入前自动把原图备份到程序根目录的 `backup\`（镜像原路径，例如 `backup\F\照片\2024\IMG_0001.jpg`），出问题可以还原。**故意不用** exiftool 的 `_original` 同目录备份：那会在照片文件夹里多出 `xxx_original.jpg`，下次扫描当成新照片索引进来，作品集里凭空多一倍
- 补写过的坐标单独存一份（`gpsOverrides`），重新扫描或清空索引后自动回填。RAW 尤其需要这道保险：exiftool 给 RAW 写 GPS 时把 GPS IFD 追加到文件尾部（NEF ~9MB、RW2 ~11MB 处），扫描读 96KB 头根本够不着，只改 `photos` 的话坐标会在下次重建记录时消失

写入由主进程调用 exiftool（参数文件 + `-charset filename=utf8`，解决中文路径；`-m` 忽略损坏的 MakerNotes）。没装 exiftool 时编辑器会提示，点「指定 exiftool」选一次即可，之后记住。

## 数据在哪

`data\`（程序目录下）。索引与缩略图都在这里，**原图不动**：

| 操作 | 索引 / 缩略图 | 原图 |
|---|---|---|
| 项目文件夹改名、挪到别的盘 | 保留 | 不受影响 |
| 整个文件夹拷到另一台电脑 | 跟着走，不必重扫 | 不受影响 |
| 清空索引 | 全部删除，点「重新扫描」重建；手动补写的 GPS 坐标保留并回填 | 不受影响 |

写入 GPS 坐标时的**原图备份不在这里**，单独放在程序根目录的 `backup\`（开发版即 `E:\www\JS\PhotoCove\backup\`，打包版即 exe 同级的 `backup\`），按原图的绝对路径镜像存放，方便直接找到、拷回还原；程序启动时就会建好这个目录，不用等到第一次写入。

只有程序目录不可写时（例如放进 Program Files），索引与备份才会一起退回系统的 `%APPDATA%\PhotoCove`。

目录行显示「不可用」通常只是外接盘没插、或文件夹被改名挪走了。插回盘后点该目录的「重新扫描」即可，不必重新添加。

## 已知限制

- **HEIC 缩略图不行**：Chromium 内核不解 HEIC，Electron 也一样，除非引入 libheif。RAW 走的是机内嵌 JPEG 预览，不受影响
- **没有代码签名**：exe 首次运行时 Windows SmartScreen 会拦一次（「更多信息 → 仍要运行」）。签名证书要按年付费，个人使用不值当；同一台机器放行一次后不再提示
- 首次扫描要为每个文件读一段文件头（主进程解析，不解码像素），四万七千张约 20 秒（其中约 5 秒是把目录 stat 一遍；RAW 现在也要读 96KB 头，存量 RAW 首次重扫会多花几秒，只此一次）；之后都走增量（比对 `size` + `mtime`），同样的库只要 5 秒左右
- 地图页一次最多列 200 张无位置照片，避免套图/截图过多时建节点卡顿

## 打包与分发

```bat
npm run dist        :: 产出 dist\win-unpacked\ ，免安装的绿色目录
```

配置在 `package.json` 的 `build` 字段里，产物约 311 MB（其中 238 MB 是 Electron 运行时本体）：

| 产物 | 说明 |
|---|---|
| `PhotoCove.exe` | 主程序，版本号、产品名、图标都已写进 exe 资源 |
| `resources\app.asar` | 网页资源（HTML/CSS/JS/vendor），2 MB |
| `data\` | 首次运行自动创建，索引与缩略图在这里 |

打包后 `data\` 必须待在 exe 旁边（`app.asar` 是只读归档，写不进数据），主进程里用 `EXE_DIR` 区分「网页资源根」与「程序根」。

只保留了 `zh-CN` / `en-US` 两种 Chromium 语言包；不做安装包（NSIS）——绿色目录更符合这个工具的使用方式，换机器直接拷文件夹。

## 自测

```bat
node_modules\electron\dist\electron.exe . --selftest --dir "F:\01照片\某个子目录"
```

会隐藏窗口跑完整链路：建目录记录 → 扫描 → 解析尺寸与 EXIF → 生成缩略图 → 用 `covefile://` 取原图并比对字节数 → 二次扫描验证增量为零。结果打到 stdout，退出码表示成败，临时数据跑完自动清掉。

**别指到整个图库**：自测有 120 秒上限，三万张会超时；指一个几十张的子目录就够。

打包后同样能自测，用来确认 asar 内的资源都找得到：

```bat
dist\win-unpacked\PhotoCove.exe --selftest --dir "F:\01照片\某个子目录"
```

界面截图（开发用）：`--shot <png> --dir <目录> --view <视图名>`，`--view` 可填 settings / help / map 等；加 `--full` 输出整页长图，用来核对帮助文档这类长页面。

主程序开着的时候，再起一个实例会静默退出（单实例锁按默认 userData 判定，而 userData 要到 `whenReady` 才改到程序目录）。开发时给参数前面加 `COVE_NO_LOCK=1` 就能跳过这把锁，用来跑自测、截图或 `--eval`；打包版不认这个变量。

## 技术要点

- **`app://cove/` 承载页面，`covefile://local/?p=<路径>` 承载原图**。不用 `file://`：它没有稳定 origin，IndexedDB 与相对路径都会受限。原图由协议层流式返回，不进 JS 堆，`<img src="covefile://…">` 直接由 Chromium 解码
- **扫描阶段的元数据在主进程解析**：主进程读文件头 96KB，就地解析尺寸与 EXIF，只回传一个小对象；页面这侧不再拿到原始字节。早期版本是把 512KB 字节搬进渲染进程、构造成 `File` 再交给 exifr，两万张就是 10GB 级的跨进程拷贝
- **为什么是 96KB**：JPEG 的 APP1(EXIF) 段上限 65535 字节，加两字节长度域结束于 65538，取 64KB 会正好切掉最后两字节、满段 EXIF 直接解不出来（本机 `BB 001.jpg` 就是）。尺寸（SOF）偶尔排在 ICC 大段之后、超出 96KB，主进程会退回一次 512KB 重试，只对这类非 RAW 文件多读
- **RAW 也只读一次 96KB 头，且不补读**：头部 TIFF 里的 EXIF（机型 / 时间 / 光圈 / ISO / GPS）读得到，宽高读不到（缩略图仍走内嵌 JPEG 预览）。早期版本把 RAW 整类跳过，结果机型与拍摄时间全丢、日期退回 mtime，还让所有 RAW 都被判成「无位置信息」；更早期则是读 512KB 直接丢掉。RAW 解析不出宽高，若沿用「没有宽高就补读 512KB」的规则，上万张 RAW 会凭空多读几 GB，而 exiftool 追加在文件尾部的 GPS 依然够不着，所以对 RAW 一律只做一次 96KB
- **手动补写的坐标单独持久化**：`gpsOverrides` 表不随 `photos` 清空，扫描时按「文件 EXIF → override → 旧记录」的优先级回填，坐标不会因文件 mtime 变化、重建记录或清空索引而丢失。`metaVersion = 2` 让存量 RAW 记录在下次扫描时强制重读一次补齐 EXIF，之后恢复增量快路径
- **读头 2 路并发**：读头花的是「IPC 往返 + 随机读」，瓶颈在延迟不在 CPU。全库 4.7 万张实测：串行 31.0 秒、2 路 22.5 秒、4 路 16.9 秒，三者元数据结果完全一致。取 2 作默认（峰值只多几十 KB，机械盘上也只多一路寻道），要更快就改 `js/scanner.js` 的 `PROBE_WINDOW`
- **进度按 100ms 节流，且覆盖「未变化」的文件**：早期只对变更文件回调，跳过的那一段在进度条上是一条纹丝不动的线，越过它才动，观感上就是「前面飞快、后面变慢」
- **必须构造真正的 `File`**。exifr 内部判断 `input instanceof Blob`，伪对象会静默失败——表现是"照片全都没有 EXIF"，而界面看起来仍有数据（拍摄时间退化成了文件 mtime）。页面侧仍保留这条 `getFile()` 备用路径，就是因为这个约束
- **元数据与图片分开存**：`photos` 只放纯文本字段（几万条也只有几 MB），缩略图与预览 Blob 单独放在 `assets` 按需读取，避免打开页面时把整个图库的二进制搬进内存
- **解码即缩放**：`createImageBitmap(src, { resizeWidth, resizeHeight })` 让浏览器在解码阶段直接降采样，比全尺寸解码再缩快数倍
- **失败状态一律不落库**：目录读不到、解码失败、超时都只记在内存，恢复后自动重试。只有「RAW 支持未开启」是合法的永久状态——早期版本把临时失败写进库，导致照片即使目录恢复了也永远空白
- **目录状态按 id 比对，不按对象引用**：`DB.listDirs()` 每次返回全新对象，用 `includes` 判断永远为假，会让不可读的目录逃过检查、扫描一路空跑
- **增量比对按「修改时间 + 文件大小」**，未变化的文件完全跳过读取
- 缩略图长边 640px、WebP，单张约 30–80 KB；大图按屏幕分辨率自适应，不超过屏幕长边的直接显示原图
- 单张解码任务 20 秒超时，避免个别文件卡住并发槽位
