# PhotoCove — 本地摄影作品展示站

桌面应用（Electron）：作品集瀑布流 / 时间轴 / 相册集 / 地图点位 / Lightbox 大图浏览，EXIF 信息展示，暗色与亮色主题。
照片始终留在原目录，只读不写；索引和缩略图存在程序目录的 `data\` 里，整个文件夹拷走就跟着走。

> v18 起**只保留桌面版**。原来的浏览器版本（File System Access API）已经移除：
> 它拿不到绝对路径、解不开 HEIC、授权每次启动都会失效，而这些限制由浏览器沙箱决定、修不好。
> 现在直接双击 `index.html` 会看到一句「请从桌面窗口启动」。

## 启动

```bat
npm install          :: 只需一次
启动 PhotoCove.bat    :: 之后双击这个
```

也可以在项目目录执行 `npm start`。

## 日常使用

- 打开就是上次扫描的结果，**不做任何自动扫描**。要更新时到「设置 → 图片库目录」点对应目录的「扫描」，或用「维护 → 重新扫描」全量检查
- **扫描只读文件信息与分辨率**（解析文件头，不解码像素），为几万张照片建索引也只要几秒到几十秒；扫描期间右下角浮卡显示进度，随时可点「取消」，已扫部分正常入库
- **缩略图按需生成**：浏览到哪张才解码哪张（滚动进入视口时生成，打开大图时生成高清预览），生成后缓存，第二次访问立即显示
- **分批加载**：每个视图每次只渲染 36 张，滚到底自动追加。几万张照片也能秒开
- 点图片进入大图：`←` `→` 或滚轮切换，`Esc` 关闭，左键点击图片进入全屏；底部缩略图条可直接点选
- 拍摄时间取自 EXIF，无效时间自动过滤（有些工具会写出 1899 年之类的畸形时间戳，宁缺勿错）
- 顶栏右侧在滚动超过 3 屏后出现「↑ 返回顶端」

### 视图

| 视图 | 说明 |
|---|---|
| 作品集 | 瀑布流，可按年份 / 器材 / 相册筛选 |
| 时间轴 | 按拍摄日期分组 |
| 相册集 | 子文件夹自动识别为相册 |
| 地图 | 带 GPS 的照片点亮在地图上，密集处聚合为数字气泡；悬停看缩略图与坐标，点击打开照片 |
| 设置 | 目录管理、RAW 开关、主题、维护与存储状态 |

### 地图与 GPSStamp

底图用**免 API Key 的 OSM 瓦片**，随项目本地存放（`assets/vendor/leaflet/`），多源自动降级：`tile.openstreetmap.de` → `tile.openstreetmap.org` → `OpenTopoMap`。三者都是 Web 墨卡托 / WGS84，与照片经纬度一致、无偏移。瓦片请求只发送瓦片坐标，不上传照片、文件名或经纬度。

地图左下角的「N 张照片无位置信息」按文件夹聚合，点一行会直接启动同目录下的 **GPSStamp**，并带 `--missing-only`：只载入那个文件夹里缺 GPS 的照片，已有坐标的不会被覆盖。填一次坐标即可补齐。

GPSStamp 是独立小工具，也可以单独使用，见 `GPSStamp\使用说明.txt`。

## 数据在哪

`data\`（程序目录下）。索引与缩略图都在这里，**原图不动**：

| 操作 | 索引 / 缩略图 | 原图 |
|---|---|---|
| 项目文件夹改名、挪到别的盘 | 保留 | 不受影响 |
| 整个文件夹拷到另一台电脑 | 跟着走，不必重扫 | 不受影响 |
| 清空本地索引 | 全部删除，点「扫描」重建 | 不受影响 |

只有程序目录不可写时（例如放进 Program Files），才会退回系统的 `%APPDATA%\PhotoCove`。

目录行显示「不可用」通常只是外接盘没插、或文件夹被改名挪走了。插回盘后点「重新检查」即可，不必重新添加。

## 已知限制

- **HEIC 缩略图不行**：Chromium 内核不解 HEIC，Electron 也一样，除非引入 libheif。RAW 走的是机内嵌 JPEG 预览，不受影响
- **尚未打包**：现在依赖 `node_modules`（约 357 MB），分发前需要 `electron-builder` 打成绿色目录
- 首次扫描要为每张照片读一段文件头，两万张的量级下耗时以分钟计，之后都走增量（比对 `size` + `mtime`）
- 地图页一次最多列 200 张无位置照片，避免套图/截图过多时建节点卡顿

## 自测

```bat
node_modules\electron\dist\electron.exe . --selftest --dir "F:\01照片\某个子目录"
```

会隐藏窗口跑完整链路：建目录记录 → 扫描 → 解析尺寸与 EXIF → 生成缩略图 → 用 `covefile://` 取原图并比对字节数 → 二次扫描验证增量为零。结果打到 stdout，退出码表示成败，临时数据跑完自动清掉。

**别指到整个图库**：自测有 120 秒上限，三万张会超时；指一个几十张的子目录就够。

## 技术要点

- **`app://cove/` 承载页面，`covefile://local/?p=<路径>` 承载原图**。不用 `file://`：它没有稳定 origin，IndexedDB 与相对路径都会受限。原图由协议层流式返回，不进 JS 堆，`<img src="covefile://…">` 直接由 Chromium 解码
- **扫描只读文件开头 512KB**。exifr 是按需切片读的，256KB 足够覆盖 JPEG 的 APP1（规范上限 64KB）与绝大多数 HEIC/TIFF 的 IFD0；整文件读意味着两万张要搬上百 GB 数据过 IPC
- **必须构造真正的 `File`**。exifr 内部判断 `input instanceof Blob`，伪对象会静默失败——表现是"照片全都没有 EXIF"，而界面看起来仍有数据（拍摄时间退化成了文件 mtime）。这是踩过的坑，自测里有专门的哨兵检查
- **元数据与图片分开存**：`photos` 只放纯文本字段（几万条也只有几 MB），缩略图与预览 Blob 单独放在 `assets` 按需读取，避免打开页面时把整个图库的二进制搬进内存
- **解码即缩放**：`createImageBitmap(src, { resizeWidth, resizeHeight })` 让浏览器在解码阶段直接降采样，比全尺寸解码再缩快数倍
- **失败状态一律不落库**：目录读不到、解码失败、超时都只记在内存，恢复后自动重试。只有「RAW 支持未开启」是合法的永久状态——早期版本把临时失败写进库，导致照片即使目录恢复了也永远空白
- **目录状态按 id 比对，不按对象引用**：`DB.listDirs()` 每次返回全新对象，用 `includes` 判断永远为假，会让不可读的目录逃过检查、扫描一路空跑
- **增量比对按「修改时间 + 文件大小」**，未变化的文件完全跳过读取
- 缩略图长边 640px、WebP，单张约 30–80 KB；大图按屏幕分辨率自适应，不超过屏幕长边的直接显示原图
- 单张解码任务 20 秒超时，避免个别文件卡住并发槽位
